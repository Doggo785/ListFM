# ListFM — Vision (validated 2026-09-09, owner: Doggo)

Source: a full review interview and four explorations (backend, frontend, debt and security, automation engine).
This file is the reference for direction on every agent run. When in doubt, follow it rather than invent a feature.

## 1. Product direction (core, non-negotiable)

ListFM = **a machine that makes playlists automatically from Last.fm**.
The core of the project, in order:
1. Visible **automations** (CRUD, recurring schedules, automatic runs).
2. **Playlists** generated by those automations, saved and browsable.
3. **History** of the runs (what, when, how many tracks, the error when one fails).

Until 1 → 2 → 3 works reliably end to end, don't start on anything else.

## 2. Non-goals (not now)

- **Social / public sharing**: a future idea, much later. Don't build for it in advance.
- **Import into streaming apps (Spotify, YouTube…)**: the product's end goal (owner, 2026-11-04), but complex and risky at scale (quotas, third-party OAuth, ID mapping). Not without the owner's explicit go-ahead; date and apps still to decide.
- **Multi-provider (Spotify, Apple, Deezer as a source)**: no, Last.fm only, for good. Product reason: only Last.fm logs *everything* a person plays; the others give a limited history, which is not a viable source.
- **Provider over-abstraction**: no generic "multi-source" layer. Stay Last.fm-first, keep the code simple.

## 3. Audience and UX principles

- **Audience**: Last.fm power users AND the general public, Spotify-style. In practice: simple by default for everyone, while complex automations stay possible (progressive disclosure: simple settings, advanced ones folded).
- **Order of quality**: **working first**, beautiful and animated after. Ugly but working beats beautiful but broken.
- **Final non-negotiables**: beautiful, animated, fast and accurate (correct filters, expected results). "Private" means: no internal data or errors exposed to clients, no needless tracking, tokens in httpOnly cookies only.
- **Settled vocabulary (2026-09-09)**: users say **Automation** for the object that defines how a playlist is generated (window, filters, schedule), and playlist / history for the result. Keep that word in the menu and the UI; don't mix it with "auto playlist". See `GLOSSARY.md`.
- **Sessions**: simple multi-device = **revoke all on login**, kept for now (like a streaming service signing out the TV when you sign in on your phone). Enough at this scale; don't make it more complex.
- **History**: date, track count after filtering (and before, as a bonus), and a detail view with **tracks and tags frozen at generation time**. An empty schedule means manual runs only.
- **Cache**: yes, in the database, so Last.fm isn't flooded (a shopping list reused instead of going back to the market for every recipe). Listens and tags are kept in the database and filters only read the database (ADR 0001, ADR 0003); tags are valid for 90 days.
- **Retries (2026-09-09)**: bounded retries that keep the original `scheduled_for` (no silent shift of the period); a manual re-run uses the same original period. The history shows when a run was planned and when it ran.

## 4. Deployment and comfort constraints

- A side project for fun, self-hosted on a small server (the owner and friends, never aiming at thousands of users). So: a single worker is fine, no Redis or Kubernetes by default, safe migrations (never `DROP CASCADE` in production), minimal Postgres backups (a nightly dump is enough).
- Infrastructure: **Docker Compose on a small Linux box**, behind an HTTPS proxy (`COOKIE_SECURE` and strict CORS are on).
- OAuth with Google and Discord plus passwords: kept as is while it works, no new OAuth provider, no forced simplification.
- Until export exists: **playlists live in the app**, and a playlist is sent to a streaming app by hand.
- Debt: the owner spent a long time fixing things endlessly and fears a bottomless pit. Rule: **stop the bleeding (P0) first, then alternate features and stability in small increments**, no big-bang security rewrite. Debt budget ~20% per iteration after P0.

## 5. Rules for agents

- Before any feature missing from `ROADMAP.md`, reread this file and check that 1 → 2 → 3 works.
- Never propose streaming export, social features or multi-provider without asking first.
- Prefer small verified diffs (red → green, plus the real surface) to large refactors.
- Explain very technical points with a one-sentence everyday picture when talking to the owner about a topic they don't know.
- When the product is ambiguous (vocabulary, cache, multi-device, history UI), ask instead of guessing.
